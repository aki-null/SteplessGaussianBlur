    Inside Stepless Gaussian Blur

    How a blur can run at any strength, cost about the same at every strength, and still look like a true Gaussian. We build it up one idea at a time, with labs you can drag and click.

    0Before you start

    This guide explains how the package's blur works, down to the fitted numbers in FittedDownUp.Generated.cs. It assumes high-school algebra and that you have written a simple blur shader before: a single-pass blur, or a horizontal pass followed by a vertical pass. Everything else is explained when it first comes up, including the details of how a GPU texture sampler really reads a texture.

    Each chapter adds one idea. Later chapters lean on earlier ones, so it reads best in order. The labs are live. They run the same formulas as the package, ported line by line from its C# and Python, and they use the package's own constants and fitted tables.

    The problem this package solves

    A Gaussian blur has one setting, sigma (σ), its width in pixels. A plain blur reads about 4σ pixels on each side of every pixel, so the cost grows with σ. Fast blurs avoid that by shrinking the image first, blurring the small image, and enlarging the result. That is a pyramid. The trouble is that a pyramid usually only offers a few fixed strengths, one per level, and the result can wobble when a bright point moves across the coarse grid.

    Stepless Gaussian Blur sets out to be:

    • fast at small strengths, where a pyramid cannot shrink the image yet;
    • about the same cost at every strength;
    • able to reach any σ, so the strength can be animated smoothly;
    • stable in motion: a moving highlight stays where it should;
    • close to a true Gaussian;
    • fragment shaders only, with one code path for every GPU.

    To get there it uses different chains of passes, called layouts, for different ranges of σ. Each range blends into the next so you never see a jump. The map below shows them on a logarithmic σ axis. By the end of the guide you will know what happens in each one and why.

    Full-res Gaussian

    Transition

    Throughout, variance means σ², and positions are measured in pixels or in texels of whichever texture a pass reads. When a number is quoted from the package, it is the package's own value.

    Part I
    Measuring a blur

    What a blur is, and the three numbers that describe one. The whole design rests on the last idea in this part: variances add.

    1A blur is a weighted average

    Look at one row of an image. It is a list of numbers, one per pixel. A blur replaces each pixel with a weighted average of the pixels around it:

    outx=∑kwk·inx+k

    The list of weights wk is the kernel, and k is the offset from the pixel being computed. The weights add up to 1, so a flat area stays exactly as bright as it was. A 2D blur does the same over a square of pixels, but for now one dimension is enough. Almost everything in this guide happens one axis at a time.

    There are two ways to look at the same blur, and both will matter later:

    • What an output pixel reads. Pick one output pixel and list the weights it gives each input pixel. This is its row of weights.
    • Where one input pixel's light goes. Light up a single input pixel and see which outputs receive some of it. This is the point response, also called the column. A bright highlight on a dark background is close to this case.

    For an ordinary blur that does the same thing at every pixel, the point response is the row flipped left to right. A Gaussian is symmetric, so the two look the same. Keep the two views apart anyway. In Part III we meet blurs that run through a half-resolution texture, and there the row and the point response really do differ.

    In short
    • A blur is a weighted average; the weights are the kernel and they sum to 1.
    • A row is what an output pixel reads. A point response is where one input's light goes.

    2The Gaussian, sigma and the taper

    The Gaussian kernel uses the bell curve for its weights:

    wk∝e−k2/(2σ2)

    The symbol ∝ means "proportional to": compute the curve at each offset, then divide every weight by their sum so they add up to 1. σ sets the width. Most of the weight sits within 2σ of the center, and at 4σ the curve has fallen to e−8, about 0.03% of its peak. So a real kernel stops somewhere. This package stops at 4σ, called the cutoff.

    Why a hard stop is a problem

    Suppose the strength animates from σ = 1.2 to 1.3. With a hard cutoff at 4σ, the kernel at σ 1.2 has taps out to offset 4, because 4σ = 4.8. At σ 1.25, 4σ reaches 5, and a tap at offset 5 appears with a small but nonzero weight. That weight was zero a moment before. On an ordinary image you would never notice, but on a very bright HDR highlight even a tiny weight is visible, and it appears all at once. Later the same thing shows up in a more serious form: a new texture fetch switching on in the shader. Any sudden change becomes a visible pop when σ animates.

    The fix is a taper: fade the curve to exactly zero over the last half-σ before the cutoff, so each new tap enters with zero weight and grows from there. The package multiplies the bell curve by a smoothstep:

    wk∝e−k2/(2σ2)·smooth(c−|k|/σ0.5),smooth(x)=x2(3−2x)

    Here c = 4 is the cutoff in σ, and x is clamped to [0, 1] before smoothstep.

    Smoothstep goes from 0 to 1 with zero slope at both ends. Inside 3.5σ it is 1 and leaves the curve alone. Between 3.5σ and 4σ it falls smoothly to 0. You will see smoothstep many more times in this guide. Every blend between two settings uses it, so nothing ever starts or stops changing abruptly.

    In short
    • σ is the Gaussian's width. The package cuts the kernel off at 4σ.
    • A taper fades the last half-σ to zero, so each new tap starts at weight zero and an animated σ never pops.
    • Smoothstep, x²(3 − 2x), is used for every blend in the package.

    3Mass, center and variance

    Three numbers describe any kernel well enough for most of this guide. They are called moments.

    mass=∑kwkcenterμ=∑kk·wkvariance=∑k(k−μ)2·wk

    These formulas assume the mass is 1. Otherwise divide the center and variance by the mass.

    • Mass is the total weight. It must be 1, or the blur brightens or darkens the image.
    • Center is the balance point of the weights. If it is not 0, the blur shifts the image sideways. A symmetric kernel always has center 0.
    • Variance is the weighted average of squared distance from the center: how far, on average, light is pushed. Its square root is the kernel's own σ. For a Gaussian kernel with σ above about 1, the variance is very close to σ². Chapter 5 shows what happens below that.

    Two kernels with the same variance can still have different shapes. A box of 3 equal weights, [1, 1, 1] / 3, has variance 2/3. A Gaussian with σ = 0.816 has the same variance but a different look. Variance measures how wide a blur is. It does not say what shape the blur has. The package controls variance exactly and works hard, in different ways, to get the shape close too.

    In short
    • Mass must be 1, center must be 0, and variance is the blur's width, σ².
    • The same variance can come with different shapes.

    4Variances add

    Blurring twice is the same as blurring once with a combined kernel. The combined kernel is called the convolution of the two. Each weight of the first kernel spreads into a copy of the second kernel, and the copies add up. Its moments follow simple rules:

    • masses multiply, so 1 × 1 stays 1;
    • centers add, so 0 + 0 stays 0;
    • variances add.
    σtotal2=σa2+σb2soσtotal=σa2+σb2

    A blur of σ 3 followed by a blur of σ 4 is a blur of σ 5, not 7. Widths do not add; their squares do.

    Why the squares add

    Follow a bit of light. The first blur moves it a random distance a, and the second moves it a further distance b, so it ends up a + b away. The variance is the average of the squared total distance:

    avg[(a+b)2]=avg[a2]+2·avg[a]·avg[b]+avg[b2]

    The two moves are independent, so the middle term splits into the product of the two averages. Both kernels are centered, so avg[a] = avg[b] = 0, and the middle term vanishes. What remains is variance a plus variance b.

    This is true for any kernels, not only Gaussians. That is what makes it useful. A downsample pass, an upsample pass and a Gaussian pass each add their own variance, and the total is simply the sum.

    Blurs tend toward Gaussians

    Repeat any small centered blur many times and the result looks more and more like a Gaussian. This is the central limit theorem. It explains why a chain of non-Gaussian passes (downsamples, upsamples, a short Gaussian) can end up looking Gaussian: each pass smooths away the oddities of the others. It is only approximate, though. The chain matches the Gaussian's variance exactly, but its shape only roughly.

    In short
    • For blurs run one after another, variances add: σ² = σa² + σb².
    • This holds for any kernels. It is the package's main bookkeeping rule.

    5Asking for a variance

    A discrete Gaussian, sampled at whole pixels and tapered, does not have variance exactly σ². At small σ the difference is large, and the taper always trims a little off the tails:

    σ asked forσ²Variance of the tapered discrete kernel
    0.50.250.2130
    110.9959
    2.45.765.7424
    24576574.37

    So the package defines its goal carefully. The target is the tapered discrete Gaussian whose curve uses σ as written. Its variance is the requested variance (BlurMath.RequestedVariance). Every layout must produce exactly this variance. That is why the variance budget at σ 24 in Chapter 19 adds up to 574.37 and not 576.

    Solving for the spread

    Usually a Gaussian pass inside a chain must supply only part of the variance, the part the other passes leave. Say it must supply 3.1 texels². Plugging √3.1 into the bell curve will not give 3.1 exactly, for the reasons in the table above. Instead the builder searches for the curve width, called the spread, whose tapered, sampled kernel has variance exactly 3.1. Variance grows steadily with spread, so a simple search works. The Python tools halve an interval until it is tiny (bisection). The C# uses a faster variant of the same idea (false position) and needs about ten tries.

    Above σ 64, computing the requested variance by summing thousands of weights would be slow. There the package uses the limit formula, σ² × 0.99717, anchored so it joins the summed value smoothly at 64.

    In short
    • The target is the tapered discrete Gaussian at σ. Its variance, the requested variance, is what every layout must hit.
    • A Gaussian pass that must supply variance V uses the spread whose tapered kernel has variance exactly V.

    6Two dimensions

    A 2D Gaussian's weight at (x, y) is the product of a horizontal weight and a vertical weight. So it can run as an X pass followed by a Y pass. This is a separable filter, as you know. The package goes further: every pass it runs, downsamples and upsamples included, is built as a product of a horizontal row and a vertical row. So the whole design can be worked out on one axis and applied to both. From here on, every kernel, budget and fit is one-dimensional unless stated otherwise.

    A practical choice comes up at small σ. A separable blur costs two passes, plus writing and reading a full-resolution intermediate texture. A single 2D pass costs the square of the per-axis fetch count. The package uses one 2D pass when a row needs at most 3 fetches (3 × 3 = 9 fetches per pixel), and X then Y passes from 4 fetches, which measured 23% faster on an Apple M4. With the default settings that switch happens at σ 0.75.

    In short
    • Every pass is a product of an X row and a Y row, so everything is designed on one axis.
    • Tiny blurs run as one 2D pass; from 4 fetches per axis, as X then Y.
    Part II
    What the texture sampler really does

    Every weight the package computes is eventually carried out by the GPU's bilinear sampler. The sampler has quirks. The package's numbers are designed around them, so they come next.

    7Where texels live

    A texture is a grid of texels. Along one axis, texel i covers the interval from i to i + 1, so its center is at i + 0.5. The pixel shader's SV_Position uses the same convention: the pixel in column 5 has positionCS.x = 5.5. To sample, a shader converts a position in texels to a UV coordinate by dividing by the texture size: uv = position / size.

    The package's shaders measure positions in texels of the texture being read, from its left edge, exactly as above. Its C# weight builders instead put texel centers at whole numbers, so texel i is at i. Both conventions give the same offsets: "half a texel to the right of center" is +0.5 either way. In this guide, offsets are always measured from a texel center.

    When a read falls outside the texture, the sampler in clamp-to-edge mode repeats the nearest edge texel. Chapter 13 explains how the package keeps clamping from distorting blurs near the image edges.

    8Bilinear filtering in one dimension

    With linear filtering on, a read between two texel centers returns a blend of the two texels. Along one axis, for a read at position x in shader convention:

    t=x−0.5,i=⌊t⌋,f=t−iresult=(1−f)·Ti+f·Ti+1

    Subtracting 0.5 shifts the coordinates so that texel centers sit at whole numbers. Then i is the texel whose center is at or just left of the read, and the fraction f is how far the read sits past that center, toward texel i + 1. Reading exactly at a center gives f = 0 and returns that one texel. In 2D the same happens on both axes, so one read blends four texels. Either way, one read is one fetch, and the fetch count is the main cost of a blur pass.

    9Two weights in one fetch

    You probably know this trick. Suppose the kernel wants a × texel k + b × texel k + 1. A single fetch can do it. Read at the fraction f = b / (a + b) past texel k's center (in shader coordinates, at k + 0.5 + f) and multiply the result by a + b:

    (a+b)·[(1−f)Tk+fTk+1]=a·Tk+b·Tk+1whenf=ba+b

    That halves the fetch count. It works only if a and b have the same sign: the fraction must lie between 0 and 1. That is one reason the package keeps every weight of every pass nonnegative. Nonnegative weights also mean no dark rings around bright points.

    A fetch has a spread of its own

    This detail matters a lot later. A fetch at fraction f is not a point. It puts weight 1 − f on one texel and f on the next, one texel apart. Its center is at f, and its variance about that center is

    (1−f)·f2+f·(1−f)2=f(1−f)

    It is zero at a texel center and largest, 1/4, halfway between. So a fetch at position x, measured from some origin, has second moment x² + f(1 − f) about that origin. In the code this is BilinearPairs.SecondMoment. Every variance the package computes for fetches includes this extra term.

    10The sampler's 1/256 grid

    Here is the first sampler quirk that shader tutorials rarely mention. The hardware does not keep the fraction f at full precision. Common GPUs store it in 8 bits, so f is rounded to a multiple of 1/256 before the blend. A fetch can only land on 1/256 steps between two texel centers. (This is called subtexel precision. Graphics APIs let it vary; the package is built around the common 8-bit case.)

    For most shaders this does not matter. For a blur that wants to keep its center and variance exact and change smoothly with σ, it does. If you ask for f = 0.4313, the sampler uses 110/256 = 0.4297, and a tiny bit of weight lands on the wrong texel. Worse, as σ animates, the true fraction glides smoothly but the used fraction jumps from step to step.

    The package handles this in three ways:

    1. It rounds the positions itself, on the CPU, before uploading them (BlurMath.Snap). Then it knows exactly where every fetch will land and can account for it. Rounding is "ties away from zero", so a fetch at −x rounds to exactly the mirror of the fetch at +x, and symmetric kernels stay symmetric.
    2. It repairs the weights after rounding, so the row's mass, center and variance stay exact. That is the next chapter.
    3. It nudges each fetch by 1/1024 texel in the shader, explained below.

    The 1/1024 nudge

    A rounded position like 3 + 110/256 sits exactly on a step. But before the sampler sees it, the shader computes uv = position × (1 / size), and the hardware turns the UV back into texels. Each step rounds in float32, so the value can arrive a hair below the step. Some GPUs truncate the fraction, always rounding down, and would then use step 109 instead of 110. Others round to the nearest step.

    The shaders add 1/1024 texel, a quarter of a step, to every read position (SampleClamped in Common.hlsl). A truncating sampler then still lands in step 110. A rounding sampler sees a position a quarter step above 110, which is less than half a step, so it also picks 110. Up to 4096 texels per axis, the float errors are provably smaller than the nudge. Above that, a fetch can land one step off, which moves under 0.4% of that fetch's weight.

    In short
    • The sampler keeps the bilinear fraction to 1/256 of a texel.
    • The package rounds every fetch position itself, symmetrically, then fixes the weights.
    • A 1/1024-texel nudge keeps float error from pushing a fetch into the wrong step on any sampler.

    11Repairing the moments after rounding

    Packing a row of texel weights into fetches, then rounding each fetch's position, leaves every fetch's weight alone but moves its position a little. The row's mass is unchanged. Its center and variance shift slightly. The package then adjusts the weights so all three are exact again. This is BilinearPairs.Restore.

    The positions cannot move (they are on the grid now), so the weights must. The adjustment is a gentle scaling of each fetch's weight:

    wi′=wi·(1+c0+c1xi+c2si),si=xi2+fi(1−fi)

    Here xi is fetch i's rounded position and si its second moment from Chapter 9. There are three unknown numbers, c0, c1 and c2, and three requirements: the new weights must give the original row's total, first moment and second moment. Each requirement is a linear equation in the three unknowns. Three linear equations in three unknowns form a small linear system, which the code solves directly by Gaussian elimination, the same elimination method used for simultaneous equations in school algebra.

    Why scale instead of adding? Scaling keeps a zero weight at zero and changes big weights more than small ones, so the shape barely moves. If the solution would make some weight negative, the code drops the last requirement and solves again, down to a single requirement if it must. When the center texel has a fetch of its own, it succeeds with all three. Chapter 12 shows a row where it cannot.

    The transition and wide layouts ask for a fourth requirement, the first moment of the even texels alone. Chapter 34 explains why. The same code handles it with four unknowns.

    In short
    • Rounding fetch positions shifts a row's center and variance slightly.
    • The package scales the weights by 1 + c0 + c1x + c2s and solves a 3×3 system so mass, center and variance are exact again.

    12Choosing which texels pair up

    A row of 2r + 1 texel weights can be paired into fetches in two ways:

    • Center alone: the center texel gets a fetch of its own, then (1, 2), (3, 4), … and (−2, −1), (−4, −3), …. This gives r + 1 fetches when r is even and r + 2 when it is odd.
    • By parity: pairs (k, k + 1) where k has the same parity, even or odd, as the output pixel. This gives about r + 1 fetches, which often saves one. An odd output pixel's row is the mirror image of an even pixel's row, so the small-layout shader stores both rows and picks one by pixel & 1.

    Parity pairing fails for tiny blurs. To see why, count fetches. At σ 0.48 the row has three meaningful texels, −1, 0 and +1. Parity pairing for an even output makes two fetches: one on texel −1 and one blending texels 0 and 1. That gives two weights to choose, but there are three requirements: mass, center and variance. Mass and center already fix both weights, so the variance comes out as whatever it happens to be: 0.1844 instead of the requested 0.1859. With the center alone, the row gets three fetches (the center and a mirrored pair), so all three requirements can be met. That is why the package keeps the center's own fetch below σ 0.74. From there the parity rows have enough fetches, and at σ 0.74 both pairings give the same row, so switching changes nothing.

    This kind of counting, how many free numbers against how many requirements, comes back in a big way in Part IV.

    Apart from that one switch, a row pairs texels the same way at every σ. If the pairing changed whenever a tiny outer weight appeared, a fetch would jump to a new place and the image would pop. With fixed pairing, a new outer fetch appears at weight zero, thanks to the taper.

    13Three precision details

    These do not change the design, but you will meet them in the shaders.

    Residual sums

    The wide and transition Gaussian passes do not compute Σ wi · si directly. They pick one fetch as an anchor and compute anchor + Σ wi · (si − anchor). On a flat image every difference is exactly zero, so the result is exactly the input, even if the float weights add up to 0.9999998 instead of 1. The precise keyword stops the compiler from rearranging the sum, which would lose this.

    Packed-float targets

    The B10G11R11 format keeps only 6 bits of mantissa in red and green and 5 in blue. Some GPUs, the M4 among them, truncate when storing into it. Every pass of a layout stores, so truncation would darken a blur by up to 4%, or 9% in blue. When the target is packed, each pass rounds its own output to the nearest value the format can hold, ties to even (PassOutput). The store then receives an exact value, whether the GPU truncates or rounds.

    Halos

    A blur near the image edge must read past the edge. A full-resolution blur with clamp-to-edge treats the outside as copies of the edge pixel. If a half-resolution intermediate texture also clamped at its own edge, pixels near the border would be blurred differently. So every intermediate texture below full resolution has a halo: three extra texels on each side (four on the transition Gaussian's axes), holding the blur of the edge-extended image. Passes read into the halo instead of clamping. A pass that reads even further clamps to the halo's outermost texel.

    In short
    • Anchor-relative sums keep flat images exact.
    • Passes round packed-float output themselves.
    • Intermediates carry a 3-texel halo so edges blur as at full resolution.
    Part III
    Blurring at lower resolution

    Shrinking the image makes wide blurs cheap, but the shrinking and enlarging passes blur too, and they behave differently at even and odd pixels. This part builds one pyramid level and its variance budget.

    14Why reduce resolution

    A full-resolution Gaussian reaches out to 4σ on each side, so it has about 8σ + 1 taps per axis. With two taps per fetch that is about 4σ fetches per axis, and twice that for the X and Y passes together. At σ 8, each pixel needs 32 fetches in X and another 32 in Y.

    Now shrink the image to half size first. A half-resolution texel is two pixels wide, so σ 8 in pixels is σ 4 in half-res texels. The Gaussian needs half the fetches per pixel, and there are a quarter as many pixels. The Gaussian's cost drops to about an eighth. Each further halving divides it by about eight again. This is why every fast wide blur works on reduced images.

    The price is two extra kinds of pass: a down pass that makes the small image and an up pass that enlarges the result. They cost fetches of their own. They also blur, and they treat even and odd pixels differently. The next chapters look at both effects.

    15Half-resolution grids and phases

    Put a half-resolution texture over its source. Half-res texel j covers source pixels 2j and 2j + 1, so in source units it spans 2j to 2j + 2, with its center at 2j + 1, on the boundary between the two pixels it covers.

    Now enlarge it back. Output pixel 2J has its center at 2J + 0.5. In half-res units that is (2J + 0.5) / 2 = J + 0.25, which is a quarter texel left of half-res texel J's center at J + 0.5. Output pixel 2J + 1 sits a quarter texel right of it. So even and odd output pixels see the coarse grid from mirrored spots. The up pass needs two sets of weights, one per phase, and they are mirror images of each other.

    The consequence is important: a chain through half resolution does not treat every pixel the same. It repeats every two pixels. A bright point on an even pixel and one on an odd pixel get slightly different point responses, mirror images of each other. And unlike in Chapter 1, an output's row is no longer just its point response flipped. The fit in Part IV checks both.

    In short
    • Half-res texel j is centered between source pixels 2j and 2j + 1.
    • Even outputs sit a quarter texel left of a coarse center, odd outputs a quarter right, so ups have mirrored weights per phase.
    • A chain through half resolution repeats every two pixels; even and odd points blur as mirror images.

    16Downsamples blur too

    The package's 2x down reads six source pixels for each half-res texel: 2j − 2 through 2j + 3, three on each side of the texel's center. The weights are symmetric. Name them by distance from the center: d0 at 0.5 pixels, d1 at 1.5 and d2 at 2.5. The six weights are d2, d1, d0, d0, d1, d2.

    Rule 1: keep the brightness

    2(d0+d1+d2)=1

    Rule 2: keep a point where it is

    This rule is less obvious, and it is the reason the package's blur stays put under a moving highlight. Light up only source pixel 0, and use C# convention, with pixel n centered at n and half-res texel j centered at 2j + 0.5. Three half-res texels read pixel 0:

    • texel 0 (center 0.5) reads it as its pixel 2j, with weight d0;
    • texel 1 (center 2.5) reads it as its pixel 2j − 2, with weight d2;
    • texel −1 (center −1.5) reads it as its pixel 2j + 2, with weight d1.

    The point's light in the small image is centered at the weighted average of those three centers. We want that to be 0, where the point really is:

    0.5d0+2.5d2−1.5d1=0

    Rule 1 gives d0 = 1/2 − d1 − d2. Substitute it: 0.25 − 0.5d1 − 0.5d2 + 2.5d2 − 1.5d1 = 0.25 − 2d1 + 2d2 = 0. So:

    d1−d2=18

    A point on an odd pixel gives the mirror-image calculation and the same rule. With both rules, a point lands in the small image exactly where it was, whichever parity it starts on. A plain 2×2 box average, which is d0 = 1/2 and nothing else, breaks rule 2: it moves a point on pixel 0 to 0.5. That is why a box-down pyramid makes a moving highlight step from texel to texel.

    The binomial down

    The binomial kernel [1, 5, 10, 10, 5, 1] / 32 gives d0 = 10/32, d1 = 5/32 and d2 = 1/32. Then 2(16/32) = 1 and 5/32 − 1/32 = 1/8, so it obeys both rules. Its variance is

    2·10·0.52+5·1.52+1·2.5232=54source pixels²

    As the sampler runs it

    Per axis the down uses three fetches: the two center pixels together (a fetch exactly between them, weight about 20/32) and one fetch on each side. The outer fetch covers weights 1/32 and 5/32, so it wants to sit 5/6 of the way toward the inner pixel. On the 1/256 grid, 5/6 × 256 = 213.3 rounds to 213. That leaves 43/256 of the fetch on the far pixel instead of 1/6. The package does not accept the resulting drift. It re-solves the outer fetch's weight so that rule 2 still holds exactly: near minus far must be 1/8, so the weight is (1/8) / (1 − 2 × 43/256) = 0.18824 instead of 6/32 = 0.1875. The down as actually run has variance 1.2559 (SmallKernel.DownVariance).

    In short
    • A 6-tap symmetric down has two rules: total weight 1, and d₁ − d₂ = 1/8 so points stay put on either parity.
    • The binomial obeys both. As the sampler runs it, its variance is 1.2559 px².

    17Upsamples blur too

    An even output pixel sits at −1/4 on the coarse grid, measured in coarse texels from the nearest coarse center. The simplest up is a bilinear read right there: weights 3/4 and 1/4 on the two nearest coarse texels. It is one fetch, and its variance is f(1 − f) = 3/16 coarse texels² (Chapter 9). But it rebuilds the image from straight line segments. The slope jumps at every coarse texel. In 2D those slope jumps can show as faint diamond and cross shapes around bright points, and they shift as the point moves.

    The package's up uses the cubic B-spline instead. It reads four coarse texels, from J − 2 to J + 1 for an even pixel, with weights from the B-spline formula at fraction 3/4:

    (1384,121384,235384,27384)

    The result is a smooth curve: its value, slope and curvature are all continuous. Its center is at −1/4, where it should be: (−2 × 1 − 1 × 121 + 0 × 235 + 1 × 27) / 384 = −96/384 = −1/4. Its variance is 1/3 coarse texels², and it is the same for both phases. It costs two fetches per axis: texels (−2, −1) in one, (0, 1) in the other. As the sampler runs it, the fractions 121/122 and 27/262 round to 254/256 and 26/256. The two fetch weights are re-solved so the total is 1 and the center stays exactly −1/4. The result has variance 0.33121 coarse texels² (SmallKernel.CubicUpVariance).

    Changing units

    Coarse variances must be converted before adding them to source-pixel variances. One coarse texel is two source pixels, so every distance doubles and every squared distance quadruples:

    variance in source px²=4×variance in half-res texels²

    So the cubic up adds 4 × 0.33121 = 1.3248 source pixels² to a blur. At quarter resolution the factor is 16, and in general it is the square of the texel size in source pixels.

    In short
    • The cubic B-spline up is smooth, centered at ∓1/4, and adds 0.33121 coarse texels² (1.3248 px²).
    • Multiply a coarse variance by the square of the texel size to get source pixels².

    18One level, and its smallest blur

    A level is a 2x down, then the rest of the blur at half resolution, then a 2x up back to the starting resolution. With only a Gaussian in the middle, the level's variance is the sum of its three parts, in source pixels²:

    total=1.2559⏟down+4g⏟half-res Gaussian+4×0.33121⏟up

    Here g is the Gaussian's variance in half-res texels². The variance the request leaves for the Gaussian is therefore g = (requested − 2.5807) / 4. That is PyramidDown.CoarseVariance.

    Notice what happens when g = 0. The down and up alone already make 2.5807 pixels², a σ of 1.61. That is the smallest blur a level can make. A request below σ 1.61 would need a negative Gaussian, which does not exist. Below that strength, a pyramid cannot be used at all, and the blur must run at full resolution. Keep this number in mind; Part IV is about it.

    In short
    • One level's down and up add 2.5807 px² by themselves: σ 1.61 is the smallest blur a level can make.
    • The half-res Gaussian gets (requested − 2.5807) / 4 half-res texels².

    19The variance budget

    Every layout in the package uses the same accounting. Add up the variance of every fixed pass, converted to source pixels². Subtract that from the requested variance. Give the remainder to the Gaussian pass, converted back to the Gaussian's texels, and solve for the spread that gives exactly that variance (Chapter 5). Here is the wide layout at σ 24, from Design.md, which the guide's own code reproduces:

    PassesVariance (source px²)
    Downs (a 4x down, then two 2x downs)62.76
    Gaussian (at 1/16 resolution)423.46
    Ups (4x cubic, then 4x bilinear)88.15
    Total, the target574.37

    The total is less than 24² = 576 because of the taper (Chapter 5). Averaged over where a point falls between pixels, every layout hits the requested variance to within 2 parts per million, ignoring GPU rounding.

    Variance is exact. Shape is not, because a chain of downs, ups and a Gaussian is not exactly a Gaussian. A single bright pixel's blur differs from the target by up to 6.2% of its brightness, summing absolute differences in 2D, and the worst of it is at σ 1.4 to 2.3. That range is the subject of the next part.

    Check yourself

    Why does the budget use variance and not σ?

    Because variances of passes run in sequence add (Chapter 4), so the leftover is a simple subtraction. With σ you would need square roots at every step: 24 is not 7.9 + 20.6 + 9.4.

    Part IV
    The fitted down/up pair

    For σ 1.62 to 2.40 the package blurs at half resolution with a down and an up whose weights change with σ. Those weights were found offline by a fit. This part explains the fit step by step.

    20The gap between full resolution and the pyramid

    Below σ 1.61 a level is impossible (Chapter 18), so the blur must run at full resolution. But a full-resolution Gaussian gets expensive quickly. At σ 2 it needs 8 fetches in X and 8 in Y, two full passes that each write and read a full-size texture.

    A plain level could take over at 1.61, but just above that point the half-res Gaussian is tiny, and running it adds two more passes (X and Y), each with its own fixed cost of setting up a draw and touching a texture. The package's answer is the fitted pair:

    • a 2x down and a 2x up whose weights are functions of σ, so the pair alone can blur by more than its fixed 1.61;
    • it runs as just two passes from σ 1.62 until a half-res Gaussian starts to grow between them, from zero width, near σ 1.72;
    • at σ 2.40 the pair's down has become exactly the pyramid's binomial and its up exactly the cubic B-spline, and the half-res Gaussian exactly a level's. The pyramid takes over there with nothing changing in the image.

    At σ 1.62, the pair costs 9 fetches per half-res texel for the down (a quarter as many texels as pixels, so 2.25 per pixel) plus 4 per pixel for the up: about 6.3 fetches per pixel, against 14 for a plain full-resolution Gaussian's X and Y passes at the same σ (7 each).

    What it costs in accuracy

    The pair cannot match the Gaussian's shape as well as a full-resolution Gaussian does. A full-resolution Gaussian is within 0.1–0.5% on the package's point test. The pair's error along one axis, from the fit's own 1D model:

    σFitted pair, as runPlain level (binomial, Gaussian, cubic)
    1.624.1%4.0%
    1.703.0%2.9%
    1.802.0%2.2%
    1.901.3%1.8%
    2.001.0%1.3%
    2.100.7%1.0%
    2.400.5%0.5%

    Summed absolute difference of a point response from the target, one axis, percent of the point's brightness. Computed in this page with the package's numbers.

    So the pair is about as accurate as a plain level where both exist, somewhat better from 1.8 to 2.1, and from 1.62 to about 1.72 it needs only two passes where a plain level would need four. In 2D the errors combine, and the worst case is about 6% near σ 1.6. That is the trade: speed in this range, paid for with shape. If that range matters for your content, BlurQuality.High skips the pair and keeps a full-resolution Gaussian up to σ 2.40.

    21Counting the knobs

    Before fitting anything, count how many numbers are actually free. Chapter 12 used the same idea in miniature.

    The down has one free number

    The down has three numbers, d0, d1 and d2, and two rules from Chapter 16. Three minus two leaves one free number. The code writes the down as a fixed starting point plus a slide along a fixed direction:

    (d0,d1,d2)=(16,1148,548)⏟DownBase+slide·(−2,1,1)6⏟DownSlide

    Check the base: 2(8 + 11 + 5)/48 = 1, and 11/48 − 5/48 = 1/8. Check the direction: its entries sum to zero, so rule 1 still holds, and its d1 and d2 entries are equal, so rule 2 still holds. A positive slide moves weight from the center taps to the outer taps. All weights stay nonnegative for slides between −0.255 and +0.204. The binomial is the point slide = −0.1786.

    The up has one free number

    The up has four weights, u0 to u3, on coarse texels −2 to +1 for an even output pixel. They must add up to 1 and be centered at −1/4. There is a third rule: the whole chain must have the requested variance. The chain's variance turns out to be simple. Measure, in source pixels, from an even output pixel to the centers of the four coarse texels its up reads: they are at −3.5, −1.5, +0.5 and +2.5. Then

    chain variance=down variance+∑i=03uici2,c=(−3.5,−1.5,0.5,2.5)

    This is Chapter 4 again. The down spreads light with its own variance, and the up then moves it by ci with probability ui. Four weights minus three rules leaves one free number for the up.

    So at each σ, the whole pair has just two knobs. That is little enough to draw: Lab 13 maps the error over both knobs as a picture. The fit's job is to set the two knobs for every σ from 1.46 to 2.40, so that the blur looks as Gaussian as possible and changes smoothly as σ moves.

    Check yourself

    From σ 1.74 a half-res Gaussian runs between the down and the up. Does that add a knob?

    Not a free one. Its variance follows a fixed schedule, described in Chapter 27: zero until curve position 1.74 (a requested σ of about 1.72), then a share of what a pyramid level would give it, reaching all of it at 2.40. The up's third rule then absorbs whatever variance is left.

    22What "close to the target" means

    A fit needs a number to minimize: a single score for how far a candidate pair is from the target Gaussian. The fit builds it on a simple model.

    The model: a line of 64 pixels that wraps around

    Take one row of 64 pixels and join its ends into a loop, so pixel 63's right neighbor is pixel 0. There are no image edges to worry about. Every filter becomes a table of weights, a matrix. Row i of the down's table lists the weights half-res texel i takes from the 64 pixels. Row i of the up's table lists the weights output pixel i takes from the 32 texels. Running one filter after another is matrix multiplication, which simply carries out "each output reads a weighted sum of inputs" twice:

    Chain=Up·Gaussian·Down(64×64)

    Row i of the chain is what output i reads. Column j is where input j's light goes, its point response. The target is a 64 × 64 table too, with the Gaussian row at every pixel.

    What gets compared

    The score lines up three kinds of feature, for both parities, against the target's (features() in model.py):

    1. Rows of an even and an odd output pixel. These decide how smooth content is filtered.
    2. Columns for a point on an even and an odd pixel. These decide what a highlight looks like.
    3. Motion: how the column changes as the point moves one pixel, even to odd and odd to even. If this differs from the target, a moving highlight shimmers. Their differences are doubled before squaring, so they weigh four times as much in the score.

    The score is the sum of squared differences over all those numbers, a least-squares error. Squaring makes every difference count as positive and punishes large misses more than small ones. It also turns the search into ordinary algebra, as the next chapters show.

    23Step 1: searching for the down

    The fit runs in three steps (fit_down_up.py). The first finds the down's slide over σ 1.46 to 1.74, the range where no half-res Gaussian runs between the down and the up.

    1. Pick nine strengths from σ 1.46 to 1.74.
    2. At each one, try candidate slides. For each candidate, find the best up for that down: the up that obeys the three rules, has no negative weight, and has the smallest score. The best up's score is the candidate's score.
    3. Keep the slide with the lowest score. The tool scans 41 slides, then refines the best one by stepping left and right and halving the step whenever neither side is better.
    4. Draw a smooth curve through the nine winning slides: a cubic Bézier (Chapter 24), fitted by least squares. That curve, DownSlideControls, is what the runtime evaluates.

    Finding the best up

    For a fixed down, the chain's features are linear in the up's four weights. Doubling a weight doubles its contribution, and contributions add. So the score is a quadratic function of the four weights, the rules are linear equations, and "no negative weight" is a set of inequalities. A problem of this kind is a small constrained least-squares problem.

    With only four weights there is a simple exact method, and Lab 13 uses it. At the best answer, some of the weights are zero and the rest are positive. Try all 16 choices of which weights are forced to zero. For each choice, solve the rules as equations together with "smallest score" (a small linear system). Throw away any answer with a negative weight, and keep the best of the rest. The tool uses an interior-point solver (positive_qp.py) that gives the same answer and also handles the much bigger problem of Step 2.

    Two things stand out in the lab. First, below about σ 1.65 the best up has u0 = 0: the valley floor runs along the bottom edge, so the "no negative weight" rule is active. Near 1.74 the best u0 leaves zero and becomes slightly positive. Second, the best slide sits close to the binomial's −0.1786 but not on it, around −0.16. Compared with the binomial, the fitted down moves a little weight from the center taps to the outer ones: at σ 1.6 it is (0.300, 0.163, 0.038) against the binomial's (0.313, 0.156, 0.031). From σ 1.74 to 2.40 the runtime then eases the down into the binomial with a smoothstep, so that it matches the pyramid at 2.40.

    24Bézier curves, in one page

    The fitted weights are stored as Bézier curves, so it is worth knowing exactly what one is. A Bézier curve of degree n blends n + 1 control values c0 … cn with weights that depend on a position x from 0 to 1:

    B(x)=∑i=0n(ni)xi(1−x)n−ici

    The blending weights are the Bernstein polynomials. The bracket is the binomial coefficient, "n choose i". In the package, x is the position along the fitted range: x = (p − start) / (end − start). Three properties make Bézier curves the right tool here:

    1. The blending weights are never negative and always add up to 1. So B(x) is a weighted average of the control values. If every control value is nonnegative, the curve is too. In the package each control point holds a whole set of weights, such as the up's four. If every control point's set obeys a linear rule, such as "sum to 1" or "centered at −1/4", every point on the curve obeys it too, because an average of sets that obey a linear rule also obeys it.
    2. The curve starts at c0 and ends at cn, so its ends can be pinned exactly.
    3. Its slope at the end is n × (cn − cn−1) per unit of x. Two equal last controls give a flat end, and joining two curves with the same end value and end slope gives a smooth join.

    25Step 2: fitting the up as curves

    With the down's curve from Step 1 and the half-res Gaussian's schedule fixed, Step 2 fits the up's four weights over the whole range, σ 1.46 to 2.40, as functions of σ. It does not solve one σ at a time. It solves for whole curves at once.

    The shape of the answer

    Each of the four up weights is two Bézier curves joined end to end:

    • degree 6, from σ 1.46 to 1.62, with u0 fixed at 0 (Chapter 28 explains why);
    • degree 16, from σ 1.62 to 2.40, where u0 starts again from zero with zero slope.

    That makes 7 + 17 control points with 4 weights each, 96 numbers, of which 87 are free once the fixed zeros are removed. They are the rows of UpControlsBeforeSplit and UpControlsAfterSplit.

    Why curves, and not the best up at each σ?

    Step 1's method could find the best up at any single σ. Storing those answers in a table would not be enough, for three reasons. The runtime needs a weight at every σ, not only at the ones that were solved. Answers found one σ at a time are not guaranteed to change smoothly from one σ to the next, and any wobble shows up as a pulsing blur when σ animates. And nothing would force the last answer to equal the pyramid's cubic up exactly, so the handover at 2.40 would jump. Fitting smooth curves to all σ at once solves all three problems.

    Why it is still a least-squares problem

    The chain is linear in the up's weights (Chapter 23). An up weight at a given σ is a weighted sum of control values (Chapter 24). So the chain's features at any σ are a weighted sum of the 96 control values. The score, summed over many σ, is a quadratic function of them, and the rules are linear equations or inequalities. It is the same kind of problem as the best up in Step 1, only bigger, and the interior-point solver handles it.

    What the score includes

    At 25 evenly spaced positions on each of the two curves, three groups of terms:

    1. Match the target: the features of Chapter 22.
    2. Match how the target changes: the rate of change of the features with σ, weighted to count about 3% as much as the matching terms. If the pair's blur grew faster or slower than the Gaussian's as σ animated, the blur would seem to pulse. These terms prevent that.
    3. Match the variance, with weight 30. Unlike Step 1, the variance here is part of the score, a strong pull rather than an exact rule. The exact fix comes later (Chapters 26 and 27).

    The hard rules

    • Every control point obeys mass 1, a centered row and a centered point response. By property 1 of Chapter 24, so does every point of the curve.
    • Every control value is nonnegative, so every weight on the curve is nonnegative.
    • The two curves join with equal value and equal slope at σ 1.62.
    • The last two controls of the second curve both equal the pyramid's cubic up as the sampler runs it. By properties 2 and 3, the curve arrives there exactly, with zero slope, so the pyramid can take over at 2.40 without a visible change in how the blur grows.

    At σ 1.46 the up is almost exactly (0, 1/4, 3/4, 0): a plain bilinear up. As σ grows, weight spreads to the outer taps, and by 2.40 it is the cubic B-spline. The fitted down stays close to the binomial throughout.

    26Step 3: the inverse table

    The curves are not indexed by σ directly. They are indexed by a curve position p, measured in the same units as variance and running from the requested variance at 1.46 to the one at 2.40. Since Step 2 only pulls the variance toward p, the chain built at curve position p has a variance V(p) that is close to p but not equal. The difference reaches 0.077 px².

    The runtime has the opposite need. It is given a requested variance v and must find the p whose chain has variance v. That means solving V(p) = v. There is a catch: in two short stretches, near σ 1.62 and 1.74, V(p) runs backward, getting slightly smaller as p grows. There, one v has up to three solutions, and a numeric search at runtime could jump to the wrong one. The blur would then jump as σ animated.

    So Step 3 solves it offline, once. For 401 evenly spaced variances it finds p by Newton's method, starting from a guess read off a fine sampling of V(p). Newton's method improves a guess by looking at how steeply V changes there and jumping to where a straight line with that slope would reach v; a few such jumps give the answer to many digits. The results form InverseTable. The tool checks that the table only rises and that every entry solves V(p) = v to 10−8. At runtime, CurvePosition interpolates the table with a Catmull-Rom spline: a cubic through each pair of neighbors whose slopes come from the entries on either side. It is smooth and needs no search.

    27What the runtime does at one σ

    Here is FittedDownUp.At(variance) in order. Every step is something earlier chapters built.

    1. Curve position. p = CurvePosition(variance), from the inverse table.
    2. Down. Evaluate the slide's Bézier at p (held at its end value above 1.74) and build (d0, d1, d2). From 1.74 to 2.40, blend it into the binomial by smoothstep.
    3. Up. Evaluate the four weights from whichever of the two Bézier curves covers p.
    4. Half-res Gaussian. A pyramid level would give it (p − 2.5807) / 4 half-res texels² (Chapter 18). The pair gives it a share of that: zero until σ 1.74, rising by smoothstep to 60% by 1.80, holding at 60%, then rising to 100% from 2.10 to 2.40. The 60% is the fit's best value. At 2.40 the share is 100% and the pair is exactly a pyramid level. These σ values are curve positions. Because p runs a little ahead of the requested variance there, the Gaussian actually appears at a requested σ of about 1.724.
    5. Up, as the sampler runs it. Pack the four weights into two fetches, round their fractions to 1/256, and re-solve their two weights for total 1 and center −1/4 (CenteredPair, the same as for the cubic in Chapter 17).
    6. Fix the variance. Rounding the up and interpolating the table leave the chain's variance slightly off. Compute what is missing: requested − (down + 4 × Gaussian + 4 × up). Then put it back. Below σ 1.74 there is no Gaussian, so the down's outer fetch weight changes. The down's variance is 2M · souter + (1 − 2M) · 0.25, where M is the outer fetch's weight and souter its second moment. So raising M by Δ adds 2Δ(souter − 0.25), and Δ is solved from that. From 1.74 to 1.80 the Gaussian takes over this job, by the same smoothstep that fades it in. Either way the variance ends up exact. Shifting the down's weight moves a point by under 0.015 pixel.
    7. Check. Every weight must be nonnegative, or the code throws.

    28Entering the pair from full resolution

    Below σ 1.46 the blur is a full-resolution Gaussian. Above 1.616 it is the fitted pair. Switching passes outright at one σ would make the image jump, because the two do not produce exactly the same blur. So from 1.46 to 1.616 the full-resolution Gaussian row turns gradually into the pair's own row.

    A chain written out as one row

    Every chain of linear passes, seen from one output pixel, is just a list of weights on source pixels. Walk backward: the output reads four half-res texels with the up's weights; each of those read six source pixels with the down's weights; multiply along each path and add up what lands on each source pixel. The result is the pair's expanded row (AddDownUp in SmallKernel.cs). There are two versions, for even and odd outputs, mirror images of each other.

    The full-resolution pass then uses the blend

    row=(1−s)·Gaussian+s·expanded pair,s=smooth(v−v1.46v1.616−v1.46)

    Because every pass is linear, blending two rows gives the same image as blending the two blurred images, but it costs only one set of passes. Both rows have the requested variance, so the blend has it too. At 1.616 the row is the pair, so the passes can switch and the image does not change.

    Why the up's u₀ is zero below σ 1.62

    Take an even output pixel at 0. With u0 = 0 its up reads coarse texels −1 to +1. Coarse texel c's down reads source pixels 2c − 2 to 2c + 3, so together they read pixels −4 to +5. The expanded pair reaches at most 5 pixels from the output. A nonzero u0 would add coarse texel −2, whose down reaches pixel −6, and the blended row would need a sixth fetch. A sixth fetch moves the row from the 5-fetch shader pass to the 8-fetch one, which measured 47% slower at σ 1.3 on M4. The Gaussian in this blend is narrowed too: its taper is set to end within 5 pixels, using the "extent" argument of BlurMath.Gaussian.

    In short
    • A chain of linear passes can be written out as one row per output parity.
    • Blending rows is blending images, at the cost of one set of passes. Every switch inside the small layout is prepared this way. Chapter 34 covers the switches where this cannot fully work.
    • u₀ = 0 below σ 1.62 keeps the blended row within five fetches.
    Part V
    The pyramid, σ 2.40 to 11.5

    From 2.40 the blur is one or two real pyramid levels. Each new level fades in through the Gaussian's weights, using the same trick as Chapter 28.

    29Levels inside levels

    A level's middle part does not have to be a Gaussian. It can be another level: a down to quarter resolution, a Gaussian there, an up back to half resolution. Levels nest, and the innermost one runs the Gaussian. The budget works the same way at every depth. A level at half resolution receives (requested − 2.5807) / 4 half-res texels². If it runs another level, that one receives (that − 2.5807) / 4 quarter-res texels², and so on. In code this is RecordPyramidLevel calling itself.

    When should a level add another level inside it? The package adds one when the new inner level's Gaussian would be at least σ 0.55 of its own texels. The second level fades in while that inner Gaussian would grow from σ 0.4 to 0.55, which is σ 3.94 to 4.22 for the whole blur. During that fade the outer level's own Gaussian is at σ 1.80 to 1.95 of its texels. There is no third level. The quarter-res Gaussian reaches 12 fetches by σ 11.5, where the transition layout takes over.

    30Fading in a level

    Adding a level changes the passes: a new down, a new up, and a Gaussian on a smaller texture. Done at a single σ, the image would jump, because a level's blur is close to the Gaussian it replaces but not equal to it. So the package does what Chapter 28 did. Before the switch, the Gaussian's row gradually takes on the effect of the level it is about to become.

    The level is linear and separable. From one output texel of the Gaussian's grid it is a list of weights on that grid's texels, worked out by walking back through the up's weights, the inner Gaussian's weights and the down's weights. That list is the virtual level. Nothing extra is drawn. The CPU computes it and mixes it into the Gaussian's row:

    weighti=(1−s)·gaussiani+s·virtuali

    Both rows have mass 1, center 0 and the requested variance. Each of those three is a weighted sum over the row's entries, so a blend of the two rows has the same three values. The blend is exactly as wide as either row, for every s. Only the shape slides from one to the other. At s = 1 the row is the level, and the next σ step can draw the level for real.

    Because the virtual level contains a 2x up, its row differs between even and odd texels. They are mirror images, for the reasons of Chapter 15. So once a fade starts, the Gaussian stage always runs as separate X and Y passes, each with an even row and an odd row.

    In short
    • A level can be written as a row on the grid it replaces: a virtual level.
    • Blending the Gaussian row into it keeps the variance exact and changes the shape gradually. At the end the level is drawn for real, and the image does not change.

    31Cheaper pieces as the blur grows

    As σ grows, the image coming out of the coarse grid is smoother, and some passes can use fewer fetches without visible harm.

    A 4-fetch down from σ 6.3

    The kernel [1, 3, 3, 1] / 8 is d0 = 3/8, d1 = 1/8, d2 = 0. It obeys both rules of Chapter 16. Its variance is 0.75. It needs only two fetches per axis, each 0.75 pixel from the coarse texel's center with weight 1/2, so four fetches in 2D instead of nine. From σ 6.3 both pyramid downs use it (FragDownHalve). From 5.9 to 6.3 the binomial turns into it: the outer fetch's far share goes from 43/256 down to 0 in whole 256ths, and its weight is re-solved each time so that rule 2 holds. The level's variance follows the down, and the budget gives the difference to the Gaussian.

    A 1-fetch outer up from σ 4.5

    From σ 4.25 to 4.5, the outermost up, the one that writes the full-resolution result, blends from cubic to bilinear: one fetch per pixel instead of four. The blend is packed into the same two fetches as the cubic, so the pass does not change until the blend is complete. A bilinear up adds less variance than the cubic (0.1875 against 0.33121 half-res texels²), and the budget gives the difference to the Gaussian (OuterLevelVariance). The inner ups stay cubic.

    Reduced output

    If you will sample the result with bilinear filtering anyway, RecordReduced skips the last bilinear up and returns the smaller texture. Your sampler does that enlargement, and the budget counts its variance in place of the skipped pass. In the pyramid, the outer up then turns bilinear earlier, over σ 2.75 to 3.

    Part VI
    Wide blurs, σ 11.5 and up

    Wide blurs shrink the image by 4 in one pass, work at 1/16 or smaller, and enlarge in two steps. They need one more fit, at the points where their passes change.

    32The transition and wide layouts

    The wide layout, from σ 24, runs these passes:

    PassGrid, in source pixels per texelWhat it does
    Quarter1 → 4A fixed 8-tap row as 4 fetches per axis (16 in 2D)
    Halve, repeated4 → … → P[1, 3, 3, 1] / 8 as 2 × 2 fetches
    Gaussian X and YPThe Gaussian, with a 5σ taper
    CubicP → P/4A 4x cubic B-spline up, four phases
    FinalP/4 → 1One bilinear fetch, a magnification by P/4

    P is the pitch: how many source pixels wide one texel of the Gaussian's texture is. It is 16 from σ 24, and it doubles at σ 70, 140, 280 and so on. Each doubling adds one more halve, which keeps the Gaussian under 32 fetches per axis. Everything but the Gaussian is fixed for a given pitch, so the blur's width is one number: the Gaussian's variance, which is the requested variance minus everything else, divided by P².

    The quarter down

    The 4x down reads 8 source pixels with weights [65, 191, 321, 447, 447, 321, 191, 65] / 2048, as four fetches with weights 1/8, 3/8, 3/8 and 1/8. Look at which pixels fall on each phase of the 4-pixel grid: pixels 0 and 4 carry 321 + 191 = 512, pixels 1 and 5 carry 447 + 65 = 512, and the other two phases also get 512 each. Every phase gets exactly a quarter of the weight. That is the 4x version of rule 1 and rule 2 from Chapter 16. A point keeps its brightness whatever phase it lands on, and its center stays within 1/128 pixel of where it was. The quarter adds 2.7578 px².

    The transition layout

    From 11.5 to 24, the transition layout bridges the pyramid and the wide layout. It is the wide layout one level finer: quarter, a halve to 1/8, the Gaussian at 1/8, the pyramid's 2x cubic up to 1/4, and the Final 4x bilinear to full resolution. Its passes never change over the range; only weights do. Its halve starts as the 6-tap binomial and turns into [1, 3, 3, 1] / 8 over 16.1 to 16.6, the same as the pyramid's down did earlier. The binomial is kept that long because halving earlier raised the error by half, past 1%. The halve runs at 1/8 resolution, so its extra fetches cost little.

    33How much a bilinear enlargement blurs

    The Final pass enlarges by a factor s with one bilinear fetch per pixel. Its variance depends on where each output pixel falls between the coarse centers. Work it out with Chapter 9's rule: a fetch at fraction f has variance f(1 − f), in coarse texels².

    For s = 2, the two output phases sit at ∓1/4 from a coarse center, so their fractions are 3/4 and 1/4. Both give f(1 − f) = 3/16. In output pixels that is 3/16 × 2² = 0.75. For s = 4, the four phases sit at ∓3/8 and ∓1/8 from the center, with fractions 5/8, 7/8, 1/8 and 3/8. The values of f(1 − f) are 15/64, 7/64, 7/64 and 15/64. Their average is 11/64, and 11/64 × 4² = 2.75 output pixels². The pattern for any power of two is

    variance=s2−16+14output pixels², averaged over the phases

    Check: (4 − 1)/6 + 1/4 = 0.75, and (16 − 1)/6 + 1/4 = 2.75. In code this is WideKernel.Magnification.

    The word "averaged" matters. Each phase has its own variance, so a single point's blur is slightly wider or narrower depending on which phase it lands on. The budget matches the average. That is the "averaged over where a point falls" of Chapter 19. The 4x cubic up has four phases too (at the same ∓3/8 and ∓1/8), each packed into two fetches with weights re-solved for its exact center. Averaged, it adds 0.33360 of its input texels².

    Check yourself: the budget at σ 24

    Pitch 16. Downs: quarter 2.7578, then halves at 4 and 8 pixels per texel, each adding 0.75 × (input texel size)²: 0.75 × 16 + 0.75 × 64 = 60. Total 62.7578.

    Ups: the cubic, 16² × 0.33360 = 85.40, plus Final by 4, 2.75. Total 88.15.

    Gaussian: 574.3696 − 62.7578 − 88.1510 = 423.46 px², which is 423.46 / 16² = 1.654 texels² on its own grid, a σ of 1.29 texels. Compare the table in Chapter 19.

    34Switches a fade cannot hide, and the second fit

    Inside the pyramid, a fade ends on exactly the level that is drawn next. At σ 11.5, at 24 and at each pitch doubling, more than the Gaussian changes:

    • At 11.5 the pyramid hands over to the transition layout with no fade. The largest remaining jump of the whole package is here. It is about as large as changing σ by 0.55%.
    • At 24 the transition's Gaussian, at 1/8, fades in a virtual level at 1/16 over σ 21 to 24, as in Chapter 30. But the wide layout then reconstructs differently: its 2x cubic up and the virtual level's 2x up give way to one 4x cubic up.
    • At each doubling, the virtual level's 2x up and the 4x cubic give way to one 4x cubic one level coarser, and the bilinear Final grows 2x. Each fade starts at 7/8 of the doubling σ, for example 61.25 to 70.

    So a virtual level that copies the pyramid's own up would not end exactly on what the next layout draws. But the virtual level's 2x up is never drawn, in the transition or the wide layout. Its weights are free to tune, and they are fitted so the blur matches the next layout as closely as possible at the switch.

    The search space

    The virtual up has two fetches per phase. Their fractions f0 and f1 are whole 256ths. Once the fractions are chosen, the two fetch weights follow from the rules: total 1 and center −1/4. So the virtual up has exactly two knobs, each an integer from 0 to 256. That is 257 × 257 = 66,049 possibilities, few enough to try every one. fit_transition.py does that for the switch at 24, and searches within 12 steps of each doubling's current pair.

    The score, and the rule for accepting a winner

    Each candidate is run through a 1D model of the passes that matches the GPU to float precision (pipeline.py), for points at 16 different phases. It gets several scores:

    • at the switch: the squared difference from the next layout's response, the largest single difference, and the difference in 2D;
    • over the fade range: the worst shape error against the target Gaussian, the worst point displacement, the worst variance error, and the worst change between neighboring σ;
    • the Gaussian's fetch count at every σ of the fade.

    A candidate replaces the current best only if it matches the switch better and is no worse on every other score and never needs more fetches. The search repeats from the winner until nothing beats it. Because of that rule, refitting can only improve quality and never cost speed. The shipped answers are (236, 49) for the switch at 24, and (221, 36), (219, 38), (220, 45), (221, 48) for the doublings at 70, 140, 280 and from 560.

    The fourth moment from Chapter 11

    The transition and wide Gaussian passes store only the even texels' row. Odd texels read it mirrored, so every pixel reads the same constant addresses, which is faster on some GPUs. Once a virtual level is mixed in, the row is no longer symmetric. Mirroring it is still correct, provided a point on an odd texel moves exactly as far as one on an even texel. That is what the fourth requirement in the moment repair keeps exact: the first moment of the even texels alone.

    35The five-sigma taper

    A 2D Gaussian built from an X pass and a Y pass, each cut off at 4σ, reaches 4σ along the axes and 4√2 σ along the diagonals. Its outer edge is a square, while a true Gaussian's faint glow is round. At a small σ nobody can see this. At a large σ on a bright HDR source, the square edge of the faint outer glow becomes visible. So the wide layout's Gaussian tapers to zero at 5σ of its own texels instead of 4σ, and the transition layout widens its taper from 4 to 5 over σ 16.1 to 16.6. This is separate from the target's own 4σ taper, which defines what the whole blur aims for.

    BudgetThe split of the requested variance among a layout's passes. The Gaussian gets what is left (19).

    Column, point responseWhere one input pixel's light goes (1, 22).
